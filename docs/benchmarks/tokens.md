# Token benchmark (TE-10)

Net tokens per successful task = all prompt + output tokens of every call, follow-up turn and retry, divided by the tasks that passed their check. Cached tokens are part of the prompt column. `always-on` is the text a variant adds to every seat prompt.

- `context:packed` (TE-03) sends the task context through the engine's context packer (`packPromptVariables`): lossless merging of repeats only, or with budget cuts as `context:packed@<tokens>`; `baseline` sends it unpacked. `--fixtures large` swaps in the bulkier review and refactor contexts. A mock seat is blind when a line its task needs (`needs` in the fixtures) is cut, so a variant that over-cuts fails instead of looking small.
- **Mock** numbers (below, regenerated with `--out`) measure prompt structure only: replies are scripted, so they cannot show behavioural savings.
- **Live** numbers come from real CLIs, run by the owner: `pnpm bench:tokens --live --budget 300000 --executor claude-code --variants <v> --gate <v>`. Paste the output under a dated heading; it is the evidence for turning a variant on by default (gate: net tokens per success down ≥ 10%, no success-rate drop, always-on text ≤ 300 tokens).
- **Caching (TE-05)** saves billed cost, not tokens: cached input is billed at a lower rate, but net tokens per success are unchanged (`cache:stable` and `cache:legacy` have the same net column; only `cached` differs). The mock's fresh (uncached) input drop for `cache:stable` over `cache:legacy` (about −30%) is a best case: sequential calls to a provider with prefix caching and a warm cache. It is unverified on live runs.

## TE-08 built-in token-saver skills (mock, 2026-11-01)

Mock numbers prove prompt-structure effects only. Each `skills:<name>` row above puts the real index line (with the shipped index header) in the prompt of every role the skill is for, and its fenced body in every call of those roles from the first call (at most 3 bodies / 4,000 body tokens per seat). That is the best case for cost (no extra `load_skill` turn) and it still costs tokens. **No behavioural saving is modelled**: the scripted replies are already at the floor the role prompts set (reviewer and planner reply with one JSON block and nothing else, builders with fixed headings), and the fixture projects are a few dozen lines, so there is nothing for "read line ranges" or "rerun one test" to save. A saving that only a real model can show (shorter replies, fewer reads, fewer suite reruns) needs the owner's `--live` run; do not read the mock rows as a verdict on that.

- The mock gate checks structure: a variant fails when its net tokens grow by more than its own always-on text explains. `plan-in-bullets` applies to one fixture task, so its cost stays within that allowance (+2.8%). `review-signal-only` passed before TE-05, but the review task is now a three-member panel, so its body is paid three times (+9.4%) and it fails. Neither meets the ship-on rule (net tokens per successful task down by 10% or more, no success drop). All eight stay off.
- The last column is what the live A/B must beat: average tokens saved per fixture task (all five tasks, not only the ones the skill applies to). The fixtures' replies average about 280 output tokens per task, so shortening replies alone can never pay back a body of this size on tasks this small. These skills can only win where real work is large: long files, long test logs, many reads.
- Enabling all eight is the owner's failure mode, reproduced: +78.5% net tokens even though a seat loads at most 3 bodies (`MAX_SKILLS_PER_SEAT`, applied in the benchmark: the first 3 eligible by name). The shipped design keeps them off, and one index line each when enabled.
- Best live-A/B candidates: `review-signal-only` and `plan-in-bullets` (smallest overhead, narrow roles). When a live run passes the gate, add the skill to `SKILL_PRESETS.lean` in `packages/engine/src/skills/format.ts` (the test in `tests/unit/skills-builtin.test.ts` then checks it against the benchmark) and paste the live output here.
- Reproduce: `pnpm bench:tokens --runs 5 --variants skills:answer-first,…,skills:all,skills:lean --gate skills:<name>`; live: `pnpm bench:tokens --live --budget 300000 --executor claude-code --variants skills:<name> --gate skills:<name>`.

## TE-06 run profiles (`--profile economy | balanced | max`, mock, 2026-11-01)

`profile:<name>` runs the real resolver (`applyRunProfile` in `packages/engine/src/config/profile.ts`) on the default config: it sends the profile's output style and skills index, and on the review task (a 3-member panel since TE-05) it asks the real narrowing (`reviewNarrowing`: `classifyRisk` on the task text, changed files and diff) whether one member is enough. Reproduce: `pnpm bench:tokens --runs 5 --variants profile:economy,profile:balanced,profile:max`.

Large fixtures: economy 3,533 vs 5,811 (-39.2%). **Read this number with care.** The whole economy saving is the review panel going from 3 members to 1 on the one fixture whose diff touches no danger area (calls 11.0 to 9.0); the other four tasks are one seat and do not move, and the always-on text is unchanged (0 tokens). It assumes one reviewer catches what three would: the mock scripts the replies, so success stays 100% by construction. Whether one reviewer misses findings the panel would catch needs the live A/B on a multi-reviewer team, and it is what the gate's "no success drop" is for. A real run saves only when 2 or more reviewers are configured and the changes touch no danger area; a danger area brings the whole panel back (tested). Not modelled by the bench: negotiation rounds (3 to 2, by construction), Lead model routing, and the economy skill preset `lean` (empty today). `max` costs the verbose fragment (+7.7%); its FULL panel is already the fixture's 3.

What `economy` does NOT switch on (the shipping gate: net tokens per success down 10% or more, no success drop), pending the live A/B:
